# Record 20261028-210000-a65f037

- **Record ID**: 20261028-210000-a65f037
- **Claim**: issue #271 (T1 item 5, kernel gate, "next lever" from DR-0013) --
  can the radix-2 carry-save Montgomery **kernel** reach 100 MHz at
  `ss_n40C_1v28` once the quotient bit q is registered, re-timed and
  fanned out from flops the flow cannot merge? Finding: **no.** The best
  working kernel is 85.00 MHz; a deliberately wrong lower-bound probe with a
  *free* next-quotient reaches only 99.14 MHz. So no quotient re-timing of
  this kernel closes the corner. The complete datapath is **not** built.
  Nothing here changes the committed design, `layout/`, or any T1 verdict.
- **Design provenance**: `rtl/modexp.v` @ `a65f037` is the committed design
  and is untouched. P1/P4/P5 are the frozen kernels of records
  `20261027-120000-98bf55d` and `20261028-190000-8b4112d`. P6-P9 are new
  timing-probe kernels frozen under
  `artifacts/20261028-210000-a65f037/candidates/rtl/`, named `modexp` only so
  the committed `flow/` requests apply (probe interface, not the modexp
  handshake).
- **Run configuration**: per kernel, one run of
  `artifacts/20261028-210000-a65f037/candidates/tools/eval.sh` (byte-identical
  to record `20261028-190000-8b4112d`'s harness): `klt synthesize` with
  `flow/synthesize-modexp.json` -> `flow/tie_constants.py` -> `klt
  place-and-route` with `flow/par-modexp.json` (tt corner, 100 MHz, seed 42)
  -> `klt sta` at the single corner `ss_n40C_1v28`, period 10.0 ns. Tools are
  the repo pin in a throwaway venv in the worktree: `klayout-tools==0.8.0`,
  `yowasp-yosys==0.68.0.0.post1208` (`yosys.wasm` sha256 verified against
  `docs/environment.md`), `ciel` PDK `open_pdks f6eeac7`. Single-corner runs
  only; the 18-corner sweep was **not** run (no kernel reached the point where
  it would be informative). `klt` was driven throughout; Yosys was never run
  directly.
- **Statistical convention**: deterministic runs. P8 (best working kernel) and
  P9 were re-run with P&R seeds 7 and 123 via `tools/eval-seed.sh`: WNS is
  -1.76435 / -1.76437 / -1.76437 ns for P8 (seeds 42 / 7 / 123) and
  identical to 5 digits for P9. So the placer seed does **not** move this
  flow's result; run-to-run variance across *netlist* perturbations (the
  1 ns noise floor in record `0011`) is still not characterized.
- **Result**: **No kernel closes; item 5 stays `unmet`; the complete design is
  not built.** Binding corner `ss_n40C_1v28`, setup, 100 MHz target
  (`f_max = 1/(10 - WNS)` as `klt sta` reports). P4 from the prior record is
  repeated for comparison.

  | id | kernel | WNS (ns) | f_max (MHz) | instances | self-check |
  | --- | --- | --- | --- | --- | --- |
  | P4 (prior record) | operand AND pre-registered, q per 4-column group | -1.635 | 85.95 | 403 | 2000 odd moduli, W=8/16, 0 errors |
  | P6 | q registered (q_r), next q from the recurrence, one flop | -6.029 | 62.39 | 420 | same, 0 errors |
  | P7 | P6 with q held in 6 non-mergeable flops | -4.469 | 69.11 | 432 | same, 0 errors |
  | P8 | P7 with next-q as a shallow XOR of flops (`x_r` pre-registered) | -1.764 | 85.00 | 428 | same, 0 errors |
  | P9 | P7 with next-q **replaced by `a[1]^b[1]`** (lower bound, wrong on purpose) | -0.087 | 99.14 | 411 | none (not a kernel) |

  Hold slack is +2.5 to +2.6 ns in every run; `timing_status` is
  `constrained`.

  - **The fan-out lever works once the copies cannot be merged.** In P7-P9
    the worst-path flop has fan-out 4-5 (P6: one flop, fan-out 44, 4.26 ns
    clock-to-Q, no buffer inserted by the flow). The six copies differ in
    polarity (q vs ~q) and flop kind (async-reset, async-set, no reset),
    which is what `opt_merge` compares; the post-synthesis netlists show no
    non-clock/reset net with fan-out above 10. This needs no `klt` feature
    (cf. `2AMLogic/klayout-tools#4538`, still open for the cleaner
    hierarchy-boundary route).
  - **But it moves the critical path onto the q recurrence.** Re-timing q
    makes q' a function of S, C, bi and q (P7 worst path: `maj3` 3.02 ->
    `xor3` 3.53 -> `o22ai` 1.46 -> `mux2_4` 2.53, 10.5 ns after clk-to-Q).
    Rewriting q' so that the operand terms are pre-registered and the odd
    modulus identity c2[0] = q is used (P8) removes about 2.7 ns of that,
    and lands at -1.764 ns: P8 and P4 are within the ~1 ns noise floor of
    each other, not a gain.
  - **P8 worst path** (10.00 arrival, 1.77 setup): flop clk-to-Q 2.19 ->
    `maj3` 3.06 -> `xnor2` 1.44 -> `nor2` 0.65 -> `o31a` (load mux) 2.66.
  - **P9 bounds the whole approach.** With the next-quotient made trivial,
    only the carry-save datapath (two chained 3:2 levels, `xor3` 3.98 ->
    `xor2` 1.23 -> `o21ai`/`a21oi`) and the registered q fan-out remain, and
    the kernel still misses by 0.087 ns (99.14 MHz). P9 is arithmetically
    wrong and is **not** a candidate; it only shows the ceiling for *any*
    quotient re-timing of this kernel is at the edge of the target with zero
    margin, below the 1 ns noise floor of the method, and that the real
    recurrence costs 1.7 ns on top.
  - Not built, and therefore not claimed: R^2 mod m, carry-save->binary
    conversion, final reduction, a modexp cocotb suite, a cycle count. No
    supersession of record `0001` Decision 3 is proposed (nothing priced).
    The kernel self-check relies on an odd modulus (Montgomery precondition,
    as in P1/P4).
