# Record 20260924-182806-3193e11

- **Record ID**: 20260924-182806-3193e11

- **Claim**: issue #143 — the Yosys/ABC mapper build is now **pinned by
  content** (`scripts/setup-env.sh` installs `yowasp-yosys==0.68.0.0.post1208`
  and verifies `yowasp_yosys/yosys.wasm` against
  `sha256:e37a7e65e3fa4efbbd64a9c1b0e906be16cdc6c4d5273109d17537f78449f38c`
  before provisioning anything else), and this record measures what record
  `20260924-134500-1a8313b`'s committed `klt synthesize` request maps to at
  that pin, so every future re-run has a stated number to compare against.

  Two results, stated separately because they are independent:

  **Result A — the pinned build maps to 1105 instances, deterministically.**
  Four runs of the same committed request at the pin (two recorded here, two
  more by this record's `rerun-pinned-synthesis.sh`) produced a
  byte-identical netlist,
  `sha256:d0785125176bc27c95adaffd25cb82dbb46da9038dfb63d5df39d7f3fb5404f7`.
  The response is identical field for field to record
  `20260924-134500-1a8313b`'s `synth-report-yosys-0.68.json` — same
  `instance_count`, `area_um2`, `sequential_area_um2`,
  `instance_counts_by_type` and `leakage_by_type_nw` — differing only in
  `run_id` and the three run-scoped output paths.

  **Result B — the frozen 1204-instance netlist is not reachable from any
  publicly installable Yosys build tried.** The same request, same frozen
  RTL, same `klt`, same PDK, same host, run under five distinct publicly
  installable mapper builds (five distinct `yosys.wasm` digests), yields
  1139 (0.65, 0.66) or 1105 (0.67, 0.68, 0.69) instances. None yields 1204.

  **This record makes no STA claim and no claim about `layout/modexp.def`.**
  It measures a mapped netlist, not a corner; nothing here places, routes,
  or times anything. It lives in `sta-corner-sweep/` because the netlist it
  measures is the *input* whose build-dependence record
  `20260924-134500-1a8313b` identified as the root cause of a 1.06 ns swing
  at that sweep's binding corner.

- **Design provenance**: RTL is the frozen bit-serial candidate
  `verification/records/sta-corner-sweep/artifacts/20260923-093000-28a7c96/candidates/rtl/modexp-bit-serial.v`
  (`sha256:b6ca7b2f…`), staged verbatim into a gitignored scratch tree as
  `rtl/modexp.v` so the frozen request's relative `sources` entry resolves to
  it. `rtl/modexp.v` on `main` is **unmodified** by this record, and no
  patch was applied to the working tree. `WIDTH=16` (the module default).

- **Run configuration**: `klt synthesize` against
  `verification/records/sta-corner-sweep/artifacts/20260924-134500-1a8313b/synth-request.json`
  (`sha256:fa8ed0e9…`), copied verbatim — `sky130_fd_sc_hd` at
  `ss_n40C_1v28`, `constraints.clock_period_ns: 10.0`,
  `constraints.dont_use` carrying the 209-cell list under the default
  `dont_use_mode: "additive"`. `klt` was `0.6.0+gc66f18fd6225`, the **same
  revision record `20260924-134500-1a8313b` used**, deliberately: the mapper
  build is then the only variable between that record's synthesis leg and
  this one. (This repo's standing `klt` pin, `dac2b5da`, predates
  `constraints.dont_use` and cannot run this request; `docs/environment.md`
  already documents the force-reinstall recipe.)

  The scratch tree was staged under the repo's gitignored `.klt/` rather
  than under `$TMPDIR`, because the pinned Yosys is a WASI build whose
  sandbox mounts a private directory over `/tmp` — a run staged in the host
  temp directory cannot read back its own generated script.

  The cross-build sweep re-ran that identical request with only `$PATH`
  changed, each entry a separate venv holding one `yowasp-yosys` release.

  **What follows for the older record.** Record
  `20260923-093000-28a7c96`'s candidate rows **2, 5 and 6** cell counts are
  **host-specific**: they were produced by a mapper build that nothing in
  that record identifies, that no publicly installable build tried here
  reproduces, and that therefore cannot be re-obtained. Any timing verdict
  derived from those rows — including row 6's 18-of-18 closure at
  +0.489 ns / 105.14 MHz — inherits that property. This does not supersede
  that record (it remains the live T1 item-5 evidence for the committed
  layout, whose own rows are a different measurement); it qualifies the
  three candidate rows named above, exactly as `docs/environment.md` now
  states.

  Note that the count is not stable even *within* the pinned wheel family:
  0.65/0.66 map to 1139 and 0.67/0.68/0.69 to 1105, with `engine_version`
  faithfully reporting the version in each case. Pinning the Yosys *version
  series* would not have been sufficient; pinning the mapper **by content**
  is what makes the number re-derivable.

  **One loose end, stated rather than smoothed over.** Record
  `20260924-134500-1a8313b` reports its netlist digest as
  `sha256:f33ededc…`; the netlist here digests to `d0785125…`, while every
  *reported* synthesis metric matches that record exactly and the generated
  `abc` line is flag-for-flag identical. That record committed the digest
  but not the netlist, so the difference cannot be diffed after the fact;
  the likeliest explanation is that the two digests were taken over
  differently derived file forms, which the issue #141 Builder pass already
  flagged as a possibility for its own third digest (`5750f29a…`) in a
  comment on issue #143. This record commits `modexp_synth-pinned.v` itself
  so that the next such comparison is a diff over bytes, not a digest
  mismatch with nothing behind it.

  untouched by it — and the multi-`WIDTH` cross-check
  (`python3 verification/cross_check.py`) passes on this commit: **2000/2000
