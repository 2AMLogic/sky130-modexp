  ### A load-bearing finding: `klt` pin bumps are not P&R-reproducible

  Re-running `klt place-and-route` with the bumped `klt`, against the
  **identical, frozen** input netlist, floorplan, seed, and PDK/OpenROAD
  version, does **not** reproduce `layout/modexp.gds` byte-for-byte, or even
  its measured metrics:

  | | Committed (`layout/modexp.gds`, old `klt`) | Fresh (this record, bumped `klt`) |
  |---|---|---|
  | Instances | 718 | 722 |
  | Die/core area (µm²) | 21969.2 / 19398.6 (identical — same floorplan) | 21969.2 / 19398.6 |
  | Utilization | 37.08% | 37.313% |
  | Wirelength (µm) | 18401 | 18281 |
  | Fmax (MHz) | 149.66 | 158.823 |
  | `def_path` content_hash | `sha256:a981054...dc31e` | `sha256:11cae8f...ee739` (different) |
  | `gds_path` content_hash | `sha256:229ed6a...7c8d10` | `sha256:596b250...e87d8` (different) |

  Same OpenROAD binary (`26Q3-1260-g06a5a02279`, the pinned
  `openroad/orfs:26Q3-296-gda37dce1c` image, unchanged), same seed, same
  netlist input hash, same PDK/deck hash — the only variable is `klt`'s own
  version, and the physical result still differs measurably. This means the
  bumped `klt`'s `write_verilog`/`write_sdf` export **cannot** be attached to
  the still-committed `layout/modexp.gds` as its own true golden reference —
  doing so would compare two different physical builds and call the result
  "LVS," which would be exactly the kind of overclaim `CLAUDE.md` forbids.
  (Separately, and even more so: a plain `klt synthesize` re-run with the
  bumped `klt` was tried first and produces a **structurally different**
  netlist — `klayout-tools#864`'s tie-literal fix changed the emitted script,
  not just the literal-tying step `flow/tie_constants.py` used to patch
  around — so re-synthesizing was rejected even earlier than the P&R
  divergence above; this record's fresh build instead reuses the **frozen,
  already-committed** post-synthesis netlist as P&R's input, isolating the
  divergence to P&R itself.)

  So item 4's LVS below is run against this record's own **fresh, internally
  self-consistent** build (P&R input netlist → P&R's own `write_verilog`
  output → extraction of P&R's own `modexp.gds`) — not against
  `layout/modexp.gds`. `layout/modexp.gds`/`layout/modexp.def` are
  **deliberately left unchanged** by this record (same reasoning issue #56's
  record already established for its own corner-sweep re-route: regenerating
  the committed, signed-off layout artifacts against a different build is
  separate, larger, not-yet-undertaken work). This is a real, useful finding
  in its own right, not a `klt` defect — a version bump changing a tool's
  physical-optimization output is ordinary (the same way a `yosys` version
  bump changes synthesis output); it just means "the same request, run again
  after a pin bump" is not a reproducibility guarantee the way "the same
  request, run again at the same pin" is (verified true at the same pin by
  issue #56's own record).

  ### LVS (item 4) — **still `status: "mismatch"`, but a fundamentally
  different, and materially deeper, comparison than before**

  `klt lvs` (engine `klayout`): `status: "mismatch"` (exit 3). `counts`: nets
  1205 (layout) / 773 (reference) / 1158 matched; devices 0/0/0 (cell-instance
  granularity, by construction, both sides); pins 753/68/1141 (subcircuit-pin
  correspondences, not just the 68 top-level I/O). **1324 mismatches**:
  888 `topology` (`"subcircuit instance could not be matched to a
  counterpart"`), 434 `net.split`, 2 `net.merged`.

  **What is resolved, compared to the superseded record**: the superseded
  record's entire 15-mismatch profile was `topology`/`"circuit could not be
  matched to a counterpart"` at the **circuit-type** level (14 unmatched
  `.SUBCKT` type declarations, cascading into the top `modexp` circuit
  itself) — the comparator never got past that block to attempt net-by-net
  correspondence at all. With the as-built reference (built from `write_verilog`,
  which — unlike the pre-CTS netlist — includes every CTS/timing-fixup cell
  and every resize the fresh layout actually contains), **every cell type
  the design uses has a same-named counterpart on both sides** (0
  LEF-fallback types when building the reference, see "Run configuration"
  above) — the circuit-type-level block is gone. The comparator now runs
  materially deeper, attempting real net/instance correspondence, which the
  superseded record's own "Reading this result" section explicitly named as
  the next, not-yet-attempted step.

  **What blocks a clean match at this depth — two separate, evidenced
  causes**:

  1. **Net-name correlation.** `klt extract`'s abstract-cells extraction
     assigns internal nets synthesized `$<id>`-style names by default, with
     no correlation to the reference netlist's own signal names (`exp_r[10]`,
     `_0099_`, ...) — confirmed directly (`grep`, no bus-indexed internal
     signal name present in the layout-side SPICE without `--def-net-names`).
     Re-running extraction with `--def-net-names` (which recovers the design's
     real net names from the DEF-net-name GDS property, `klayout-tools#951`)
     measurably improves the result — `net.merged` mismatches drop from 48 to
     **2**, `net.split` from 480 to **434**, `topology` from 913 to **888** —
     but does not resolve it fully.
  2. **Extraction-deck layer coverage.** The fresh extraction's own
     `warnings[]` (present regardless of `--def-net-names`) report **3367
     routing-stack clusters (4172 shapes) that join no extracted net** (dead
     metal — no via lands on it and no same-layer wiring touches it) and
     **1137 shapes on 15 layers outside the `sky130` deck's connectivity
     graph** — the extraction's own documentation states plainly that "a net
     routed only through [such geometry] extracts as multiple disconnected
     nets instead of one, which will silently mismatch a downstream `klt
     lvs` reference netlist." This is a real, cited, tool-documented
     limitation of the `sky130` extraction deck's layer coverage on a design
     of this routing complexity — not a connectivity defect this design
     introduced, and not something a reference-netlist change can work
     around. `net.split`'s 434 mismatches are consistent with exactly this
     mechanism.

  **Overall for item 4: real, evidenced progress (circuit-type matching
  achieved for the first time; the net-name-correlation half of the residual
  gap has a working fix, `--def-net-names`), but not a clean LVS.** Stated
  plainly, not qualified away: `spec/modexp.md`'s Signoff row remains **not
  met**. The residual gap is now attributed to a *different*, deeper, and
  better-understood cause (extraction-deck layer coverage) than the
  superseded record's cause (CTS/resize insertions the pre-CTS reference
  didn't model) — that cause is fully resolved. Closing the remaining gap
  needs either a `sky130` extraction-deck layer-coverage extension or a
  different LVS methodology (e.g. transistor-level extraction); both are
  natural follow-ups, not attempted here, consistent with the precedent the
  superseded record's own "Reading this result" section already set for
  exactly this kind of not-yet-attempted deeper step.
